# BNPL SQL Analytics

A small SQL project that analyzes a **"buy now, pay later" (pay in 4)** database: sales, merchants, late payments and customer behavior.

> **All data is fictional.** Customers, stores and amounts are invented and generated by a script with a fixed random seed. This is a learning project, not data from any real company.

## What this project shows

- Designing a small relational schema (4 tables, keys, constraints and indexes)
- Generating consistent test data with Python (`seed.py`)
- Answering business questions with SQL: sales trends, top merchants, late payment rate, risky customers, repeat buyers
- Checking data quality with SQL (queries that must return zero rows)

## How it works

Each purchase (**order**) is split into **4 installments**, one every 14 days. The first installment is paid at checkout.

```
customers ──< orders >── merchants
                │
                └──< installments
```

| Table | What it stores |
|-------|----------------|
| `customers` | Who buys (name, city, signup date) |
| `merchants` | The stores (name, category) |
| `orders` | One row per purchase (customer, merchant, date, total) |
| `installments` | The 4 payments of each order (due date, amount, paid date, status) |

Installment status: `paid`, `paid_late`, `overdue` (due date passed, still unpaid) and `pending` (due date in the future).

The "current date" in the data is fixed at **2026-11-01**, so the results are the same every time you run the project.

## How to run

You only need Python 3 (SQLite comes with it). No extra libraries.

```bash
python seed.py          # creates the database (bnpl.db)
python run_queries.py   # runs all 15 queries and prints the results
python run_queries.py Q06 Q10   # runs only the queries you list
```

## Tests

The project has automated tests (28 tests, Python standard library only):

```bash
python -m unittest discover -s tests -v
```

They check that:

- the generated data is complete and consistent (4 installments per order, installments add up to the order total, no payments before the order or in the future, no broken foreign keys)
- the database rejects bad data (invalid status, negative amounts, duplicate installments, unknown customers)
- the data generation is deterministic (two runs produce exactly the same data)
- every query in `queries.sql` runs, the data quality queries return zero rows, and key results (such as the late payment rate) match an independent calculation in Python

The tests were also checked by breaking the code on purpose (for example, removing a database rule) and confirming that a test fails.

## Queries (`queries.sql`)

| # | Question | SQL concepts |
|---|----------|--------------|
| Q01 | Business overview (customers, orders, GMV, average order) | `COUNT DISTINCT`, `SUM`, `AVG` |
| Q02 | Sales by month | `GROUP BY`, `strftime` |
| Q03 | Running total and month-over-month growth | CTE, `SUM() OVER`, `LAG` |
| Q04 | Top 10 merchants and their share of sales | `JOIN`, window function over an aggregate |
| Q05 | Sales by merchant category | `JOIN`, `GROUP BY` |
| Q06 | Late payment rate (overall) | `CASE`, conditional aggregation |
| Q07 | Late rate by due month | `GROUP BY` over time |
| Q08 | Late rate by installment number | `GROUP BY` |
| Q09 | How many days late are the late payments? | `julianday` (date math) |
| Q10 | Customers with the most overdue installments | 3-table `JOIN`, `HAVING` |
| Q11 | Risk flag: customers who are late too often | CTE, rule-based filter |
| Q12 | Repeat customers (1, 2-3, 4+ orders) | CTE, `CASE`, percentage with `SUM() OVER ()` |
| Q13 | Signup cohorts | `LEFT JOIN` |
| Q14 | Data quality: installments add up to the order total | `HAVING` (must return 0 rows) |
| Q15 | Data quality: nothing paid before the order existed | `JOIN` (must return 0 rows) |

## A few results

With the default seed:

- 300 customers, 784 orders and about R$ 142 thousand in sales (GMV)
- **4.78%** of installments that were already due are late (paid late or still unpaid)
- The first installment is never late (it is paid at checkout); installments 2, 3 and 4 are between **6.5% and 6.8%**
- 31% of customers bought only once; 24% bought 4 times or more
- Q11 finds a handful of customers with a late rate above 30%, the kind of signal a risk team would review

## Notes

- **SQLite** was chosen so anyone can run the project with no installation. The queries use standard SQL, with a few SQLite functions (`strftime`, `julianday`) for dates.
- Amounts are stored as `REAL` for simplicity. In a real payments system, money should be stored as integer cents or `DECIMAL` to avoid rounding errors.
- The customer "risk profile" used to generate late payments is **not** stored in the database, so the queries have to discover the pattern from the data.

## How this project was built

This is a **learning project**. I built it with the help of an AI assistant, and I use it to study and practice SQL.

- **What the AI assistant helped with:** designing the schema, writing the data generator, the first version of the queries, and the automated tests.
- **What the project is for:** practicing the SQL concepts listed above (joins, aggregation, CTEs, window functions, data quality checks) on a realistic "buy now, pay later" scenario, and reading and explaining each query.
- **Data:** everything is fictional (see the note at the top).

I am open about using AI because I think it is a valuable tool for learning and for productivity, as long as I review, test and understand what it produces.
